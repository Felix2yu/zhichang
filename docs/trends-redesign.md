# 健康趋势页重设计方案

> 目标：解决「51 个指标逐个点选」的选择效率问题，并让「几天一测」与「一天数十条」这两类
> 频率差异极大的指标在同一页面里各自得到合适的表达。
>
> 适用范围：`web/src/routes/trends/+page.svelte`、`web/src/lib/components/MetricTrendCard.svelte`、
> `web/src/lib/metric-activity.ts`、`web/src/lib/metric-groups.ts`。

---

## 0. 结论摘要

| 维度 | 现状 | 新方案 |
|---|---|---|
| 组织轴 | 苹果健康 12 分类（与数据可用性无关） | **数据频率档**为主轴，分类降为次筛选项 |
| 选择方式 | 逐个点 chip，无搜索/批量/持久化 | 频率分区 + 搜索 + 组内全选 + 常用持久化 + URL 同步 |
| 同屏规模 | 每指标一张 ECharts 卡（51 张 = 51 canvas） | 三种视图：聚焦（1）/ 网格（≤12）/ **列表（51 行 SVG 迷你图）** |
| 图形形态 | 所有指标一律 line/bar + category 轴 | **按点数量分 5 档**切换形态，一律真实时间轴 |
| 稀疏数据 | 时间轴被压缩，断点不可见；空态只有一句话 | 阶梯/点列图 + 间隔标注 + 密度条 + 可回溯 + 空态可行动 |
| 请求策略 | 进页面发 2 次 `api.daily`，每次点击再发一次 | `api.coverage` 替代第二次全量拉取；点击 debounce + 增量取数 |

**一句话**：把「指标」从**同质的卡片**改造成**按数据节奏分档呈现的对象**——
密集的画趋势，稀疏的画间隔，只有一次的画记录，没有的不占版面。

## 1. 现状与问题（附证据）

### 1.1 指标选择：51 个 chip 的平面罗列

`web/src/routes/trends/+page.svelte:214-238` 把 12 个分组的指标全部平铺成 chip 云。

- 无搜索框、无组内全选、无批量操作（`:121-128` 只有 `toggle` / `clearAll`）。
- 选择结果 **既不写 localStorage 也不写 URL**（对比：概览页写了 `TREND_STORE_KEY`，
  睡眠页把区间写进 URL）。刷新即回到硬编码的 `['step_count','heart_rate']`（`:22`）。
- chip 上看不出该指标有没有数据，只有悬停提示「最近一次更新 N 天前」（`:66-71`）。
  **用户必须点进去才知道是空的**——这是最直接的无效点击来源。
- 每次 `toggle` 都立刻 `load()`，连点 8 个指标就是 8 次 `api.daily`。

### 1.2 图形：所有指标共用一套形态

`MetricTrendCard.svelte:115-122` 的 X 轴是 `type: 'category'`，刻度直接取后端返回的点：

```ts
xAxis: { type: 'category', data: points.map((p) => p.date.slice(5)), ... }
```

后端 `daily_metrics_day` **只存有数据的日期**（`internal/store/postgres/query.go:39-42`
是 `WHERE local_date BETWEEN` 直接查，不补零）。于是：

> 一个在 1-03、3-28、8-12 各测过一次的指标，画出来是**相邻的三个点**。
> 「两个月没测」这个最重要的事实被抹掉了。

其余缺口：

- 无周/月粒度聚合（全仓无 `granularity` 参数）；365 天视图画 365 根柱子。
  睡眠页已有 `web/src/lib/sleep-buckets.ts` 的 `grainFor/bucketMean`，趋势页没复用。
- `smooth: true`（`:136`）对 3 个点的序列同样生效——连线是编出来的。
- 稀疏指标的卡脚仍显示 均/高/低（`:221-227`），3 个点的极值没有统计意义。
- 未画常态参考线（概览页 `TrendChart` 有 `targetLine`，趋势页没有）。

### 1.3 规模：ECharts 实例随选择数线性增长

每张卡 `onMount` 里 `echarts.init` + 一个 `window.addEventListener('resize')`
（`MetricTrendCard.svelte:152-163`）。选 20 个指标 = 20 个 canvas + 20 个 resize 监听。
这是当前设计的硬上限隐患。

### 1.4 请求：进页面固定两次全量拉取

`trends/+page.svelte:149-166` 为了算活跃度，额外拉一次 **全部 51 指标 × 90 天**的
`api.daily`，且不随选择变化。而 `/api/coverage?days=90` 已经用一次 `GROUP BY`
返回每个指标的 `days` / `last_date` / `days_since`
（`internal/store/postgres/insights.go:204-246`），前端也已有 `api.coverage`
（`web/src/lib/api.ts:573`）——这次全量拉取是可以整块删掉的。

## 2. 设计原则

1. **频率优先于分类。** 分类（苹果健康心智）保留为次筛选项，但不做版面主轴——
   它回答的是「这是什么」，而用户在这里真正要问的是「这个有数据吗、多久一次」。
2. **有多少点，画什么图。** 图形形态由**区间内实际点数**决定，而不是由 `kind` 决定。
   3 个点不许画折线，1 个点不许画图。
3. **时间轴必须是连续的时间。** 全部档位统一 `xAxis.type: 'time'`，
   间隔就是间隔，不压缩。
4. **稀疏指标展示「间隔」而不只是「数值」。** 低频指标的信息量在
   「多久测一次、比上次变了多少」，不在曲线形状。
5. **空态要可行动。** 「无数据」要区分「今天还没同步」「这个区间没有」
   「从来没接入」三种，并给出下一步（换区间 / 回溯 / 去数据源页）。
6. **同屏规模与图形成本解耦。** 扫描 51 个指标时用 SVG 迷你图，不用 ECharts。

- 稀疏行（点 < 6）的「走势」列渲染成**密度条**：一根细线上每次测量一个刻度，
  一眼看出节奏，而不是画一条 3 点的假曲线。
- 点击任意行 → 进入该指标的聚焦视图。

## 4. 指标选择方式

### 4.1 主轴换成频率分区

分区由 `/api/coverage?days=365`（一次 GROUP BY）算出，与 51 项指标字典做差集：

| 分区 | 判定（365 天窗口内有数据的天数） | 典型指标 | 计数来源 |
|---|---|---|---|
| 日更 | ≥ 183（半数以上） | 步数、活动能量、心率、静息心率、睡眠、站立 | coverage |
| 定期 | 24 ~ 182（约每月至少一次） | 体重、体脂、VO2max、饮水量 | coverage |
| 偶发 | 1 ~ 23 | 血糖、血压、肺活量、六分钟步行、身高 | coverage |
| 未接入 | 0 | （差集）心律恢复、步行不对称性… | 字典 − coverage |

> **窗口取 365 天，不是 90 天。** 实施时实测发现：90 天窗口会把「上一次测量在 224 天前」
> 的肺活量判成「从未接入」——一年测两次对它来说完全正常，把它和真正没接过的指标归为一类，
> 恰好是这个分区要解决的问题的反面。阈值按窗口比例算（`freqBounds`），
> 改窗口长度时结论自动跟着变。

**未接入分区默认折叠**，只显示「17 项从未同步」。这直接消除当前设计里最大一块无效点击。
展开后 chip 置灰，悬停提示「字典已登记，尚无数据」，并给一个跳数据源页的链接。

### 4.2 交互清单

1. **搜索框**：匹配 `display_name_zh` 与 `metric` id，支持拼音首字母
   （`tz` → 体重、`xlfh` → 心肺相关）。51 个指标必须能搜。
2. **频率分区 tab**（上表），默认落在「日更」。
3. **分类筛选 chip 行**：12 个苹果健康分类，与频率分区**交叉过滤**（交集）。
4. **批量**：每组一个「全选本组」；分区 tab 上给「全选本区」；顶部「清空」。
5. **常用持久化**：选择写入 `localStorage`（新增键 `zhichang.trend-selected`，
   在 `prefs.svelte.ts` 的 `LOCAL_PREF_KEYS` 里登记，让「重置本机偏好」能一并清掉）。
6. **URL 同步**：`?m=step_count,body_mass&days=90&v=list`，可分享、可后退。
   默认选择（自动挑选或 localStorage 里的既有选择）与默认区间不写进地址栏，
   只有用户显式改过选择、区间或视图时才出现参数，避免链接变长。
   （睡眠页已有先例 `sleep/+page.svelte:344-348`。）
7. **默认选择**：不再硬编码 `['step_count','heart_rate']`，改为
   「日更分区里活跃度最高的前 6 项」——有数据才算数。
8. **请求合并**：`toggle` 后 200ms debounce 再发请求，且只传**新增**的指标
   （已加载的序列留在内存里，取消选择不删数据，只从视图移除）。

### 4.3 chip 上的信息

每个 chip 右侧带一个状态点 + 年龄文字，不靠悬停也能看见：

- `●` 品牌色：今天有数据
- `●` 次级灰：N 天前（N ≤ 3 不显示文字，避免噪音）
- `○` 空心：未接入

## 5. 图表展示逻辑

### 5.1 形态分档（由区间内实际点数 n 决定，节奏慢的一律降档）

| n | 档位 | 图形 | 连接线 | 符号 | 卡脚指标 |
|---|---|---|---|---|---|
| ≥ 24 | **连续** | line（瞬时）/ bar（累计） | 实线，`smooth` 关 | 隐藏 | 均 / 高 / 低 |
| 6 ~ 23 | **点线** | line | 实线细，`smooth` 关 | 常显 4px | 均 / 高 / 低 |
| 2 ~ 5 | **阶梯** | line + `step:'end'` | 实线（状态型）/ 虚线（事件型） | 常显 5px + 数值标签 | 本次 / 上次 / 变化 / 间隔 |
| 1 | **单次** | 不画图 | — | — | 数值 + 日期 + 「上次 X（N 天前）」 |
| 0 | **空态** | 不画图 | — | — | 见 §6.4 |

状态型 vs 事件型的区分放在新建的 `web/src/lib/metric-render.ts`：

```ts
// 状态型：测完一次，值一直成立到下次测量 → 阶梯
// 事件型：每次是一次独立事件，中间没有「值」→ 点列 + 虚线
const STATEFUL = new Set(['body_mass','body_mass_index','body_fat_percentage',
  'lean_body_mass','height','vo2_max','sleeping_wrist_temperature']);
```

**只看点数会出错。** 实测：体重在 365 天区间里有 9 个点，点数上够「点线图」，
但这 9 个点跨了整整一年——连成折线会读成连续变化，而真实信息是「每次称完这个值保持了多久」。
所以 `tierOfPoints(n, dates)` 会综合节奏：点数够但**中位间隔 > 9 天**（每周及更慢）的，
一律降为阶梯档。间隔标签在点数 > 8 时自动省略，否则十几个「42 天」会盖住图本身。

> ⚠️ 这张表**不要**写进 `metric-groups.ts`。该文件被
> `internal/domain/metric/ui_contract_test.go` 用正则解析，改动数组结构会让契约测试变红。
> 新增独立的 `metric-render.ts` 模块最安全。

### 5.2 统一改用真实时间轴

所有档位 `xAxis.type: 'time'`，`series.data` 传 `[date, value]` 对。
这一条改动同时修复了「断点不可见」和「间隔被压缩」两个问题。

配合 `axisLabel.formatter` 按档位给不同格式：连续档 `MM-DD`，稀疏档 `YY-MM-DD`
（跨月才看得出来）。

### 5.3 粒度聚合（仅连续档）

把 `sleep-buckets.ts` 的逻辑抽成公共的 `web/src/lib/trend-buckets.ts`，
按区间跨度自动选档（沿用现有阈值，保持全站一致）：

| 跨度 | 粒度 |
|---|---|
| ≤ 45 天 | 逐日 |
| 46 ~ 180 天 | 按周 |
| > 180 天 | 按月 |

**关键差异**：原 `bucketMean` 一律取均值，对累计量是错的。分桶必须按 `day_agg` 分口径：

- 瞬时量（`day_agg ∈ {mean,max,min,last}`）→ 桶内均值
- 累计量（`day_agg = sum`，如步数/能量）→ 桶内**日均**（sum ÷ 有数据的天数），
  并且轴名改为「步数 日均」，否则 7 天的桶和 1 天的桶在同一根轴上没法比

空桶不出柱（`bucketMean` 现有行为，保留）。

### 5.4 Y 轴与常态线

- 保留现有 `axisFmt` 的「万」压缩逻辑。
- 连续档增加一条 **常态虚线**（`/api/baseline` 的 30 天中位数），与概览页 `TrendChart`
  的 `targetLine` 对齐。稀疏档不画——3 个点算不出常态。

### 5.5 卡片不再同质

卡头、图形区高度、卡脚三处都随档位变化（稀疏档图区降到 96px，把空间让给
日期标注与间隔说明；连续档维持 150px）。不再是一张卡套所有指标。

## 6. 稀疏数据处理方案

这是本方案的核心。稀疏指标的问题不是「点少画不好看」，而是
**「多久没测」「比上次变了多少」才是它真正的信息，而现在的图把这两点都丢掉了。**

### 6.1 卡头：最新值必须带日期

稀疏档的卡头数值旁强制标注记录日期：

```
体重                    68.5 kg
08-12 记录 · 40 天前     ▼ 0.3
```

现在的实现（`MetricTrendCard.svelte:187`）直接把最后一个点当「最新值」显示，
40 天前的体重看起来跟今天的步数一样新鲜。这是必须修的。

### 6.2 阶梯/点列图：把间隔画成距离

有了真实时间轴（§5.2），`step:'end'` 的横线长度**就是**「这次值保持了多久」：

```
体重 (kg)
  70 ┤  ●━━━━━━━━●
  69 ┤            ╰━━━━━━━●━━━━━━
  68 ┤                            ╰━━━━●
     └──┬────┬────┬────┬────┬────┬────┬──
      01-08 02-19 04-02 05-14 06-25 08-12
             41天   42天   42天   48天
```

- 每个点标数值，相邻两点之间标间隔天数（>30 天时用警告色）。
- 状态型用实线阶梯，事件型（血糖、血压）用虚线连点，不暗示中间有值。

### 6.3 密度条：一眼看出测量节奏

稀疏行/卡底部加一条 4px 高的年度刻度条（近 365 天，每次测量一根 1px 竖线）：

```
体重  ▪────▪────▪────▪────▪────▪    每 42 天一次，近一年 9 次
血糖  ▪─▪──────▪─────────────────▪  不规律，近一年 5 次
```

这条比任何文字都直观地回答了「这个指标多久测一次」，也让
「为什么它排在后面」有据可依。数据来自同一指标 365 天的 `api.daily`。

### 6.4 空态分三种，且都可行动

现在只有一句「近 N 天无同步记录」（`MetricTrendCard.svelte:211-216`）。改为：

| 情况 | 文案 | 动作 |
|---|---|---|
| 区间内无、但历史有 | 近 30 天无记录 · 上次测量 08-12（40 天前） | **[显示最近 6 次]** 按钮 |
| 从未接入 | 尚未同步过数据 | 跳数据源页的链接 |
| 今天还没同步 | 今日数据尚未同步 | 无（自动恢复） |

### 6.5 稀疏档自动回溯（n < 3，默认开）

n < 3 时，图形没有意义。默认把取数窗口**回溯到最近 6 次记录**（上限 365 天），
并在卡头明确标注：

```
区间内 1 次 · 已回溯至最近 6 次（近 214 天）        [关闭回溯]
```

- 实现：收集所有需要回溯的指标，**合并成一次** `api.daily`（metrics=这批指标,
  from=今天-365），不逐指标发请求。
- 可在卡片上单独关闭，关闭后回到区间内的原生数据。

### 6.6 卡脚：稀疏档不显示极值

| 档位 | 卡脚内容 |
|---|---|
| 连续 / 点线（n ≥ 6） | 均 / 高 / 低（现有逻辑保留） |
| 阶梯（2 ≤ n < 6） | 本次 / 上次 / 变化 / 间隔 N 天 |
| 单次（n = 1） | 记录日期 / 上次值 / 变化 |

3 个点的「最高 / 最低」是噪声，不是信息。

## 7. 数据请求与性能

| 项 | 现状 | 新方案 |
|---|---|---|
| 活跃度/密度元数据 | `api.daily` 全 51 指标 × 90 天（全量序列） | `api.coverage?days=90`（一次 GROUP BY，约 51 行） |
| 选择变更 | 每次点击发一次全量 `api.daily` | 200ms debounce + 只取新增指标 |
| 稀疏回溯 | 无 | 合并为一次 365 天 `api.daily` |
| ECharts 实例 | 随选择数线性增长（上限 51） | 聚焦 1 个 + 网格 ≤ 12 个；列表 0 个（SVG） |
| resize 监听 | 每卡一个 `window` 监听 | 一个共享监听广播到已注册实例 |
| 图表库体积 | `import * as echarts` 全量 | 可选：改为按需引入（独立优化项） |

**净效果**：进页面的请求减一次（且是最大的一次），选择过程请求数从 O(点击次数)
降到 O(1)，ECharts 实例数从 51 降到 ≤ 13。

### 修正过程中发现的两个连带问题

1. **「显示最近 6 次」在单次档缺失 → 回溯开关变单向。**
   关掉回溯后，若区间内还剩 1 次记录，卡片落到「单次」档，而按钮只挂在下空态上，
   于是再也打不开。修法：单次档同样给入口——它和空态一样是「信息不足」。

2. **自动回溯会把「今日尚未同步」这条空态吃掉。**
   区间内一个点都没有但一两天前还有数据时，回溯先把前几次记录翻出来填满，
   于是永远显示不出「今天的数据还没到」。这不是「测得少」，是同步还没跑完。
   修法：新增 `isPendingSync()`，这种情况不自动回溯；用户显式点按钮时通过
   `forceBackfill` 覆盖。

### 验证结果（桩后端 + 无头浏览器）

| 场景 | 实测 |
|---|---|
| 密度条（体重，30 天区间） | 「近一年 9 次」——旧行为下这里只有 1 根且被挤到边缘 |
| 网格 → 聚焦 | 点卡片后 URL 变 `v=focus&f=step_count`，返回按钮出现 |

| 空态 stale（VO2max，7 天区间，上次 70 天前） | 「近 7 天无记录 / 上次测量 2026-08-12 · 70 天前 / 显示最近 6 次」 |
